Mini-Netflix: migrate it, then break it on purpose

Netflix took seven years to move from its own data center to AWS, and invented chaos engineering along the way. We reproduced the same journey with a small movie-catalogue app, then measured what happened when we broke it.

Moving to the cloud is not enough. The architecture is what makes a system survive failure, and the only way to prove it is to break it on purpose.

The Netflix case

August 2008: a database corruption stopped Netflix shipping DVDs for three days. The cause was single points of failure.

The problem
  • One data center, one monolith, one vertically scaled database
  • Hardware ordered months ahead for unpredictable streaming growth
  • Running data centers was "undifferentiated heavy lifting"
The decision
  • Not a 2nd data center (keeps cost and the monolith)
  • Not lift-and-shift (keeps every software single point of failure)
  • Move to AWS and rebuild cloud-native: 7 years, done Jan 2016
The result
  • Toward 99.99% availability; 130 new countries in Jan 2016
  • Cloud cost per stream start "a fraction" of the data center (a side benefit)
  • Video still on its own CDN, Open Connect: hybrid

Principles we followed in every experiment: define a steady state (home page returns 200 within 1 s), hypothesise it continues, inject a real-world failure, try to disprove the hypothesis, keep the blast radius small.

Our architecture

One Docker image for every stage. Only configuration changes, so any difference in the results comes from the architecture, not the code.

S1 · rehost
  • One t3.micro in us-east-1a, public IP, Amazon Linux 2023
  • Monolith + Postgres containers on the same VM (infra/s1)
  • Containers restart if the VM restarts, but nothing replaces the VM
  • terraform apply: 33 s
S2 · refactor
  • ALB path routing: / → catalogue, /recommendations/*, /login
  • ASG min 2 / max 4 across 2 AZs, ELB health checks, CPU target tracking (50%)
  • Every instance runs catalogue, recommendations and auth; stateless
  • Data in RDS Postgres; security groups: ALB → app → DB only
  • terraform apply: ~7.5 min (mostly RDS)

Chaos on AWS: lift-and-shift vs refactor

  
Replays of the real runs on 14 Nov 2026, us-east-1. Every bar is one second of recorded home-page requests.

  

    
    
  

  

  
What to point at. S1: the only instance is stopped at 63 s; the "operator" restarts it 60 s later and the VM is back, but availability never returns, because a restarted EC2 instance gets a new public IP (44.203.10.200 → 3.239.110.80) and clients still use the old one. S2: three kills; each time the load balancer keeps serving from the survivor, the ASG launches a replacement within 2 s, and healthy instances return to 2 after 114–176 s. The short red dips are the ~20 s it takes the ALB health check (2 × 10 s) to notice a dead target, which is why E1 landed at 98.92%, just under 99%.

  
What to point at. The Chaos Gorilla idea: every instance in us-east-1a is terminated at once. us-east-1b keeps serving, the ASG rebuilds capacity in about 143 s, and availability is 99.47% with a longest gap of 4 s. Only one failure happened in this run, so it met the 99% SLO.







  
Load and scale-out

  
What happens when traffic grows: one machine saturates, while the Auto Scaling Group adds servers on its own.

  

    
    
  

  

  
What to point at. Desired capacity goes 2 → 3 → 4 with no human action (the CPU target was lowered from 50% to 30% at about 7:20, because CPU levelled at 43–48%). Throughput rises from about 305 to 370 req/s as instances join. One overloaded instance fails its health check and is replaced; the first replacement is refused by the new account's vCPU quota and the ASG retries a minute later. Honest caveat: almost all the red is client-side timeouts on our laptop (24,421 of 24,423 failures; only 2 were HTTP 502). The laptop load generator saturated at ~300 req/s, so the 500 ms latency criterion (H4) could not be judged.

  
What to point at. One machine: p95 stays under 50 ms up to ~225 req/s, then climbs and flattens around 185 ms above ~290 req/s, where the single machine saturates. There were no errors. This is the curve the S2 Auto Scaling Group is meant to flatten by adding servers.

Breaker experiments, recorded

  
The 5-minute runs behind the live demo. The fault starts at 60 s and lasts 120 s.

  

    
    
  

  

  
What to point at. Breaker ON: the bars turn amber (fallback) but never red; availability stays at 100.0% in all three runs, and 40.5% of home pages used the fallback, which matches the 40% of the run the fault lasted. Breaker OFF: every home page returns 502 for the whole 120 s; availability is 59.6%. Same app, same failure; only the design differs.

  
What to point at: slow is worse than down. Without the breaker there are almost no errors, but p95 jumps from ~20 ms to 803 ms and throughput falls 30% (95 → 67 req/s), because every request waits on the slow call and threads run out. With the breaker, the 250 ms timeout turns "slow" into "failed", the fallback is served, and p95 stays at 21 ms.

What it shows
      
    
        
  • The cloud wins for small or variable workloads: you pay only for the hours you use.
    • 
        
  • Owning wins for huge, steady workloads. Steady demand breaks even earlier, because elasticity is worth less when demand is flat.
    • 
        
  • At Netflix-like 100 PB/month, an own CDN is about $0.13 M/month against $2.1 M on CloudFront.
    • 
        
  • That is exactly Netflix's hybrid choice: AWS for the control plane ("the brain"), Open Connect for the video bytes.
    • 
        
  • A $5/month AWS Budget alert was created first, and everything was destroyed after each session.
    • 
      

  







  
Limitations and conclusion

  

    
Limitations (said up front)
      
    
        
  • One AWS run per experiment, so no range; S2 E1 missed 99% by only 0.08 points.
    • 
        
  • The laptop load generator saturated at ~300 req/s, so H4's latency criterion could not be judged.
    • 
        
  • S1's restart was scripted at exactly 60 s; a real on-call engineer is slower, so S1 is if anything optimistic.
    • 
        
  • India → us-east-1 adds ~200 ms, so AWS and local latencies are not comparable.
    • 
        
  • 3 services and at most 4 instances: no retry storms, deep dependency chains or replication lag.
    • 
        
  • RDS was single-AZ and everything was in one region; FIS templates were written but not run.
    • 
        
  • The cost model uses list prices that were not re-checked against the calculators.
    • 
      

    
With more time or budget
      
    
        
  • Repeat every AWS run three times.
    • 
        
  • Run the load generator on EC2 in the same region.
    • 
        
  • Run the FIS templates and compare them with our boto3 Chaos Monkey.
    • 
        
  • Enable RDS Multi-AZ and test a database failover.
    • 
        
  • Add a second region with Route 53 failover (Chaos Kong).
    • 
        
  • Pre-baked AMIs or Fargate for faster recovery.
    • 
      

  

  
Rehosting moved the single point of failure into the cloud. Refactoring removed it. And we only know that because we broke it on purpose.
